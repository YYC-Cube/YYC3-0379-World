# 冻结策略 — FREEZE POLICY（封版 / 热修 / 例外）

> 冻结 = 暂停**非修复类**变更进入发布链；修复/回滚/安全处置永不受冻结限制。

## 一、冻结类型

| 类型 | 触发 | 冻结范围 | 时长 | 宣告方式 |
| --- | --- | --- | --- | --- |
| **发版封版**（code freeze） | tag 候选确定后 | C2/C3/C4 新变更；C0/C1 文档与修复例外 | Release 完成即解 | issue 置顶 + 群公告 |
| **事故冻结** | SEV1 事故处置中 | 一切非处置变更（避免干扰根因定位） | 事故关闭即解 | 事故档宣告 |
| **审计冻结** | 全链审计执行中（S1-S15 型） | 业务特性 PR（审计批自身变更除外——本仓审计批即大量修复） | 审计收口即解 | 审计 INDEX 宣告 |
| **维护窗口** | NAS/网关计划内操作 | 依赖目标服务的部署与测试 | 窗口结束 | ops 公告 |

## 二、热修（Hotfix）流程

**定义**：冻结期内为 P0/P1 缺陷走的加速通道。

```
1. 分支：hotfix/<PATCH 号> 自 main（或自上一 tag）
2. 最小修复：只含缺陷修复（顺手的重构/文档 = 拒绝）
3. 门禁：全量 12 命令（**不缩水**——热修最忌门禁打折）
4. 发布：PATCH tag 直发（跳过封版，FAILBACK：缺陷重现即回滚 R1-R6）
5. 合回 main + CHANGELOG Security/Fixed 条目
```

**判例锚定**：本仓 hotfix 实形态 = S11 settings 内容协商修复（当天发现→修复→NAS 部署→e2e 固化）——热修不是"免检"，是"免排队"。

## 三、例外审批

| 请求 | 审批人 | 条件 |
| --- | --- | --- |
| 冻结期合入非修复变更 | 发布官 | 书面理由 + 影响面评估 + 可独立回滚证明 |
| C4 冻结期强制 | 架构师+发布官双人 | 仅限安全处置（如紧急撤 API） |

## 四、解冻条件（全部满足）

1. 触发事由关闭（Release 发出 / 事故关闭 / 审计收口）；
2. 冻结期积压变更批量评审（不自动放行）；
3. 解冻公告（含积压清单）。
