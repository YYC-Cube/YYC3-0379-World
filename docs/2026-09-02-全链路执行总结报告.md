## 二、重大发现与根因档案

### 2.1 NCCL int32 溢出已被 NVIDIA 修复（最重要修正）

- **历史定档**: 2026-08-10 审核报告将 NCCL 跨节点死锁定性为"永久架构约束"（GB10 双机 121GB×2 UMA 对称虚拟地址超 int32 → `malloc -24,805,113,728 bytes`），据此采纳 ADR-4（放弃 TP=2，服务级分工）
- **今日实测**: `nvcr.io/nvidia/pytorch:26.07-py3`（**NCCL 2.30.7+cuda13.3**）双机 rank0/rank1：init → 64MB → 1GB → **16GB 大缓冲映射** all_reduce 全部通过，双端 EXIT=0
- **结论**: 根因是 NCCL 版本而非硬件。**TP=2 部署条件 = 推理容器捆绑 NCCL ≥2.30**（宿主机 NCCL 版本不阻塞）
- **改档位置**: 《DGX-Spark双机推理部署指南》§5.2 已更新

### 2.2 双机服务全灭的统一根因

8/29 的目录清理**掏空了两台 DGX 的本地模型目录**（`/home/yyc3/models/*` 只剩空壳）+ NAS 挂载丢失（挂载点变空目录）→ 所有依赖本地模型路径的服务连环崩溃：

| 服务 | 症状 | 恢复方式 |
|------|------|----------|
| N1 yyc3-vllm-service | vLLM 配置校验失败（/models 无 config.json） | QSFP 取模型重建（§4.1） |
| N2 yyc3-embedding/reranker | FileNotFoundError 模型路径 | HF 镜像源下载回原路径，崩溃循环自动恢复（§4.2） |
| N2 yyc3-node | app.js 不存在（**运维手册 §8.2 已知问题**：入口硬编码） | 待用户 sudo 停用（fix-n2.sh 已部署） |

### 2.3 网络真实拓扑（重要认知修正）

- **DGX 双机与 NAS/Mac 不在同一物理网络**（192.168.3.x 只是同号网段；N1 ping N2 通、ping NAS 不通）
- 双机 ↔ NAS 仅 Tailscale 可达，实测 **~2MB/s（受 NAS 上行带宽限制）**——大文件传输不可用
- 双机间 QSFP 直连 **实测 ~1GB/s**（200Gbps 线速级别）——一切大对象传输应走此通道
- N1 fstab 中的 SMB 挂载走 Tailscale IP 100.65.172.88（曾误改 LAN IP 导致挂载失败，已还原）

### 2.4 统一用户 yyc3（运维标准）

《YYC3-Node-运维手册》（N1 `/home/yyc3/nvidia-workbench/`）明确：**统一运行用户 yyc3**，历史 yyc3-101/-102 部署属跨用户权限问题根源。实测 `yyc3@` 可密钥直连双机；N1 免密 sudo，N2 sudo 需密码。设备侧 `~/nvidia-workbench/`（真身在 /home/yyc3/）含：vllm-local-models-compose.yml、start-local-vllm.sh、YYC3-Node-运维手册、12 类官方目录、NVIDIA-NIM 报告副本、ngc_health_check.sh；N2 另有 `/opt/ngccli`（NGC CLI 4.21）与 `~/NVIDIA AI Workbench`。

## 七、已解事故：NAS sshd 认证间歇性故障（10:25 发生，10:45 自愈）

> ✅ **10:45 更新：ssh 已自愈恢复，部署桥验证正常。** 根因确认为 **TOS sshd 防暴力惩罚机制**：持续高频连接压力下会间歇性拒绝有效公钥乃至密码（自愈窗口约 15-20 分钟）。此结论一并解释了 §5.3 的全部"谜题"（ECS 三客户端被拒/Mac 时通时拒/CI 认证失败）。**运维规约：对 NAS 的自动化连接须限频（≥60s 间隔）；Mac 部署桥 cron 已是 2 分钟粒度安全。**原恢复指引保留备查。

**现状**：NAS sshd 对 YYC3 用户**公钥 + 密码全拒**（Mac 持续 4 连拒；密码通道 expect 测试亦拒）。最后一次成功连接 10:25 前后；此前已出现"同钥同用户时通时拒"的不稳定模式（§5.3 ECS 谜题同源）。

**影响面**：Mac 部署桥失效（NAS 无法接收新部署）；生产网关不受影响（容器继续运行，公网 200）。

**疑似诱因**（按可能性排序）：① TOS 安全层对 `/etc/ssh` 篡改尝试（10:24 的 chown 尝试，虽全报 EPERM）做出反应；② sshd 高频连接后的惩罚状态未解除；③ TOS sshd_extend 包装层异常。

**恢复指引（用户执行，按序尝试）**：
```bash
# A. 等待 10-30 分钟后重试（惩罚类通常自愈）
ssh yyc3-45 "hostname"
# B. 若仍拒：TOS Web 管理界面（浏览器）登录 → 终端/服务管理 → 重启 SSH 服务
# C. 或 NAS 物理控制台/键盘登录:
sudo systemctl restart sshd   # 或 TOS 等价服务名
# D. 恢复后验证部署桥: bash ~/yyc3-deploy/watch.sh && tail ~/yyc3-deploy/watch.log
# E. 若复发：检查 sshd_extend 机制与 /etc/ssh 权限链，考虑固化 PerSourcePenalties 配置
```
