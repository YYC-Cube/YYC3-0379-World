# 零停机热切换与版本管理规范（📋 规划稿）

> **状态警示**：Shadow/Canary/蓝绿/别名切换均未实现（现状切换 = 改 env 重启网关，见 [01](01-接入现状规范-v2.3.md) §5）。依赖 [02](02-Registry目标架构.md) Registry 落地。

## 1. 切换模式总览

| 模式 | 适用场景 | 流量切换 | 回滚时间 |
| --- | --- | --- | --- |
| **Shadow** 影子 | 新模型初验证 | 0%（仅复制） | 立即（不占流量） |
| **Canary** 金丝雀 | 灰度发布 | 5% → 100% 渐进 | ≤30s |
| **Blue-Green** 蓝绿 | 重大版本升级 | 100% 秒切 | ≤10s |
| **Weighted** 权重 | 多模型负载均衡 | 按权重分流 | 立即 |

> 现状近似能力：env 上游 `priority`/`weight` 字段已支持静态权重分流（✅ 生产），可视为 Weighted 模式的手动形态。

## 2. 版本命名规范

```
格式: <major>.<minor>.<patch>[-<prerelease>][+<build>]

major: 不兼容变更（权重格式 / 端点契约）
minor: 向后兼容新功能（新能力 / 新参数）
patch: 向后兼容修复
prerelease: alpha / beta / rc
build: 构建日期 / git hash
```

## 3. 别名与实例状态机

### 3.1 alias 机制（📋 规划）

`model_alias`（公网 API 调用名）→ 映射 `model_id`（含版本）；版本切换 = 修改别名指向，**不中断公网 API**。同一别名可映射不同 model_id。

### 3.2 实例生命周期四态（统一自原 A 规范）

```
offline → loading → ready → draining → offline
  离线     加载权重   承接流量   排空待下线
```

### 3.3 健康三态（统一自原 B 规范，与生命周期分用）

```
healthy / degraded / unreachable
```

### 3.4 draining 排空语义（整合关键决策）

> 原 A 规范 draining 与原 B 蓝绿「观察期保留 Blue 热备」为同一语义，统一为：
> **draining = 不接新流量，等待存量 SSE/流式长连接自然完成后下线**。蓝绿切换观察期内旧版本即处 draining 态，可秒切回。

### 3.5 无缝版本切换流程（别名切换）

1. 新版本实例部署 + 注册，`ready`；别名**不指向新版本，不接公网流量**。
2. 冒烟验证新版本功能。
3. 管理面修改别名映射 v1 → v2；Registry 推事件，网关路由表实时更新（新请求走 v2，存量 SSE 在旧实例完成）。
4. 旧版本置 `draining`，等待活跃请求排空。
5. 排空确认后下线旧实例；保留版本记录用于回滚。

## 4. Shadow 影子流量

生产流量复制到新模型验证，**不影响响应**：

```yaml
shadow:
  enabled: true
  primary: "deepseek-v4-flash"
  shadow: "qwen3.8-flash-next"
  sample_rate: 0.1                 # 10% 复制
  compare_metrics: [latency_p95, error_rate, output_length, output_hash]
  auto_promote:
    conditions:
      - "shadow.latency_p95 < primary.latency_p95 * 1.1"
      - "shadow.error_rate < 0.01"
      - "shadow.output_match_rate > 0.85"
    observe_duration_minutes: 30
```

状态机：`inactive → observing →（达标）ready for canary /（未达标）rejected`

## 5. Canary 金丝雀

```yaml
canary:
  baseline: "deepseek-v4-flash"
  stages:
    - { weight: 5,   duration_minutes: 30 }
    - { weight: 10,  duration_minutes: 30 }
    - { weight: 30,  duration_minutes: 60 }
    - { weight: 50,  duration_minutes: 60 }
    - { weight: 100, duration_minutes: 0 }
  auto_rollback:
    conditions:
      - "canary.error_rate > 0.02"
      - "canary.latency_p95 > baseline.latency_p95 * 1.3"
      - "canary.ttft_p95 > 3000"
```

## 6. 质量门禁（Promotion Gate）

任何版本进入下一阶段前必须通过：

```yaml
shadow_to_canary:
  - "shadow.observe_duration_minutes >= 30"
  - "shadow.error_rate < 0.01"
  - "shadow.latency_p95 < baseline.latency_p95 * 1.1"
  - "shadow.output_match_rate > 0.85"
canary_to_full:
  - "canary.total_requests >= 1000"
  - "canary.error_rate < 0.005"
  - "canary.latency_p95 < baseline.latency_p95 * 1.15"
  - "canary.uptime >= 0.999"
```

## 7. 回滚决策树与触发条件

```
发现问题
  ├─ P0（服务不可用 / 数据错误）→ 立即自动回滚 ≤30s + critical 通知
  ├─ P1（性能退化 >30% / 错误率 >5%）→ 5min 内自动回滚
  ├─ P2（性能退化 <30%）→ 告警 + 人工判断（确认→手动回滚 / 观察→记录）
  └─ P3（观察性问题）→ 记录 + 下次迭代
```

**自动回滚硬条件**：`error_rate > 0.10 within 5min` / `p95 > baseline×2.0` / `ttft_p95 > 5000ms` / `consecutive_5xx > 50`。

**回滚操作**（依赖 Registry）：

```bash
# 快速回滚（自动寻上一稳定版本）
curl -X POST https://api.0379.world/registry/v1/models/{model_id}/rollback \
  -H "X-API-Key: ${ADMIN_KEY}" -d '{"auto": true, "reason": "紧急回滚"}'

# 指定版本回滚
curl -X POST .../rollback -d '{"target_version": "v4.0.0", "reason": "v4.0.1 性能退化"}'
```

## 8. 模型下线

1. 实例置 `draining`，等待活跃请求排空。
2. 移除 alias 指向；状态 `offline`。
3. 注册 Agent 停止心跳；网关自动摘除上游。
4. NAS 仓库资产**保留归档不删除**（便于重新上线）。
