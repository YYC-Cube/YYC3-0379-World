# 模型接入现状规范（生产基线 v2.3.0）

> **范围**：本文档仅收录**生产代码已实现**的接入机制（✅ 标注），以及 NAS 资产层管理规范。
> Registry 动态注册、热切换等未落地机制见 [02](02-Registry目标架构.md)/[03](03-热切换与版本管理.md)，**禁止将规划条目当现状引用**。

## 1. 架构约束（三条铁律）

1. **API 网关不加载权重文件**：网关仅做鉴权、限流、路由转发、可观测；权重全部由后端推理服务（vLLM/NIM/Ollama）加载。
2. **NAS `/Volume1` 仅作只读资产仓库**：生产推理必须使用算力节点本地 SSD 缓存模型；NFS 挂载仅用于调试。
3. **所有后端推理服务必须实现 OpenAI 兼容接口契约**，网关不做模型业务适配。

## 2. 模型资产仓库规范（NAS 层）

> 路径根目录：`/Volume1/yyc3_hd/data/`

### 2.1 目录组织

```
/Volume1/yyc3_hd/data/
├─Qwen/                 # Qwen 系列全部 HF 模型
├─DeepSeek/             # DeepSeek 系列
├─GLM/                  # GLM 系列
├─MiniCPM‑V‑4.6/        # 多模态
└─…其他模型家族
```

每个模型版本独立 `snapshots/{版本标识}` 目录，示例：
`/Volume1/yyc3_hd/data/Qwen/Qwen3.8-Flash-Next/snapshots/master`

### 2.2 文件要求（HF 标准模型）

必须包含，缺失则判定资产不完整：

- `config.json`、`generation_config.json`
- `tokenizer.json`、`tokenizer_config.json`、`vocab.json`、`merges.txt`
- `chat_template.jinja`
- `model.safetensors.index.json` + 全部分片 `model-xxxx-of-xxxxx.safetensors`
- LICENSE、README.md（可选，建议保留）

### 2.3 完整性校验（入库必做）

📋 **规划待实现**：校验脚本 `core/scripts/model_asset_verify.py` 尚未创建。当前入库校验为人工执行以下三项：

1. 统计 safetensors 分片数量，与 `model.safetensors.index.json` 权重映射清单比对，确认无缺失。
2. safetensors 文件头部校验（`model-*.safetensors` 前八字节 magic），识别截断、损坏。
3. tokenizer、config 配置文件存在性校验。

校验失败模型**禁止上线到 API 网关**。

### 2.4 模型分发策略

1. **调试场景**：算力节点 NFS 只读挂载 NAS 模型目录直接加载，仅用于开发测试。
2. **生产场景**：算力节点执行增量同步（📋 脚本 `model_sync_to_node.py` 待实现，当前手动 rsync），把 NAS 原版模型同步到节点本地 NVMe SSD；vLLM 读取本地 SSD 路径，规避 NFS IO 抖动。
3. NAS 仓库永远只读；模型更新只在 NAS 本机执行，更新后重新完整性校验。

## 3. 后端模型服务部署规范（vLLM）

### 3.1 启动强制约束

1. 生产模式必须读取**算力节点本地 SSD 路径**，禁止直接 NFS 挂载路径承接生产流量。
2. 必须开启健康检查端点 `/health`；建议同时提供 `/healthz` 轻量探活。
3. 必须启用 `/v1/models` 端点，返回自身模型信息。
4. 不同模型实例**必须使用独立端口**，容器隔离，一个实例 OOM 不影响其他实例。
5. 禁止公网直接暴露推理端口；只允许内网访问；公网流量全部经 YYC³ 网关转发。

### 3.2 vLLM 最小启动模板

```bash
vllm serve /home/yyc3/models/Qwen3.8-Flash-Next \
  --served-model-name qwen3.8-flash-next \
  --port 8000 \
  --host 0.0.0.0 \
  --max-model-len 32768 \
  --trust-remote-code
```

## 4. 网关上游池机制（✅ 生产实况）

> 代码锚点：[upstream_registry.py](../../core/api/services/upstream_registry.py)。本节全部为已实现行为。

### 4.1 上游配置（env 静态通道）

`OPENAI_COMPATIBLE_UPSTREAMS`（JSON 数组），网关启动时解析为运行时上游实例：

```json
[
  {"name":"dsv4-head","base_url":"http://yyc3-101.local:8001/v1","models":["deepseek-v4-flash"],"priority":1},
  {"name":"dsv4-worker","base_url":"http://yyc3-102.local:8001/v1","models":["deepseek-v4-flash"],"priority":2},
  {"name":"asr-n2","base_url":"http://yyc3-102.local:8004/v1","models":["qwen3-asr-1.7b"],"priority":1}
]
```

**字段语义**（与代码一致）：

| 字段 | 说明 |
| --- | --- |
| `name` / `base_url` | 上游名与内网地址（`http://ip:port/v1`） |
| `models` | 模型匹配模式列表（fnmatch 通配，如 `qwen*`） |
| `capability` | 能力分组（chat/embedding/rerank/asr/ocr，默认 chat） |
| `priority` / `weight` | 数字越小越优先；同级按权重分流 |
| `capacity` | 并发容量（默认 32），路由参考 |
| `api_key_envs` | 多 Key 轮询环境变量列表（429 自动跳下一把） |
| `sovereign` | 主权标签：`X-YYC3-Sovereign: required` 请求仅路由到此 |
| `fallback_url` | 同一上游备用地址（QSFP 主 / Tailscale 备） |
| `health_path` | 健康检查路径（默认 `/health`） |

解析失败仅告警降级为空池，**绝不 crash**（高可用语义）。

### 4.2 熔断与验活（✅ 生产）

| 机制 | 参数 | 行为 |
| --- | --- | --- |
| 连续失败熔断 | 阈值 3 次 / OPEN 30s | 摘除 → 30s 后半开单请求探测 → 成功恢复 |
| 主动验活降级 | 连续失败轮数累计 | 权重×0.5（不摘除，恢复即复原） |
| EWMA 统计 | alpha=0.3 | 延迟 / 错误率指数滑动均值，供路由参考 |

> 注：原规范声明「错误率>15% 自动降级」，生产代码**无此逻辑**（EWMA 错误率仅统计），已列入规划候选（见 [05](05-监控告警与Runbook.md)）。

### 4.3 响应头契约（✅ 生产）

| 响应头 | 说明 |
| --- | --- |
| `X-YYC3-Upstream` | 实际处理请求的后端实例名 |
| `X-YYC3-Degraded` | 是否走降级路径 |
| `X-A2A-Cost` | A2A 任务计费成本（仅协同事务端点） |

### 4.4 model_registry 表（⚠️ 现状仅基础字段）

[db.py](../../core/api/db.py#L58) 中 `model_registry` 表当前仅 6 字段（id/display_name/backend_type/backend_name/enabled/created_at），用于 `/v1/models` 列表动态扩展。完整 Registry Schema（capabilities/心跳/版本/审计）为规划，见 [02](02-Registry目标架构.md)。

## 5. 新模型上线流程（现状通道）

1. **资产入库**：模型完整文件放入 NAS 仓库 → 完整性校验（§2.3）。
2. **同步到节点**：手动 rsync 至算力节点本地 NVMe SSD（📋 脚本待实现）。
3. **启动 vLLM 实例**（§3 约束），本地验证 `/v1/models`、`/health`。
4. **配置上游**：在目标环境 `.env` 的 `OPENAI_COMPATIBLE_UPSTREAMS` 追加上游条目 → 重启/热载网关。
5. **冒烟验收**（见下）。
6. 开放公网访问。

### 冒烟验收用例（上线必全过）

1. ✅ 模型资产完整性校验通过（无缺失分片、无损坏 safetensors）。
2. ✅ vLLM `/health` 返回正常。
3. ✅ 网关 `/v1/models` 可查询该模型。
4. ✅ 基础 chat 推理（同步）返回正常 JSON。
5. ✅ SSE 流式调用 chunk 输出正常。
6. ✅ 响应头 `X-YYC3-Upstream` 指向正确后端实例。
7. ✅ 异常边界：超长输入返回正确错误码。
8. ✅ 多模态模型（VL/ASR/Rerank）执行对应能力冒烟。

## 6. 容量与约束

1. **注册模型版本数**：env 通道无硬限制；📋 Registry 落地后 PG+Redis 可管理数百版本（大量可处 offline 归档态）。
2. **同时在线实例数**：受算力 GPU 显存硬约束（yyc3-101 / yyc3-102），网关本身不限。
3. 业务建议：高频模型常驻显存；低频模型按需加载、空闲超时卸载。

## 7. 故障排查清单（现状通道）

| 现象 | 排查点 |
| --- | --- |
| 新模型公网不可见 | ① env JSON 是否合法（解析失败静默空池）② 网关是否重启/热载 ③ base_url 网络连通性 |
| 调用返回 503 上游不可用 | ① vLLM `/health` 是否正常 ② 是否被熔断摘除（30s 半开自愈）③ models 匹配模式是否命中（fnmatch） |
| 冷启动加载极慢 | 是否直接 NFS 挂载；切换本地 SSD 缓存 |
| safetensors 报 invalid header | 分片损坏，从 NAS 重新同步该分片 |
| 429 频繁 | 配置 `api_key_envs` 多 Key 轮询 |
