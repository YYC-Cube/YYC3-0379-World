## 一、七项目技术核心项拆解

### 1.1 litellm —— 请求生命周期工程化（最值得借鉴）

源码级请求流（[ARCHITECTURE.md](file:///Users/yanyu/YYC3-GitHub/GitHub-API/litellm/ARCHITECTURE.md) 已实读）：

```
Client → proxy_server → user_api_key_auth(Redis优先查Key) → hooks(并行限流/缓存控制)
      → Router(fallback→retry) → SDK main → Handler → ProviderConfig.transform_request/response
      → cost_calculator(tokens×price) → 响应头 x-litellm-response-cost
      → async_success_handler → DBWriter(Redis队列→PG批量落库)   ← 全异步，DB写不进请求路径
```

**四个可直接移植的核心项**：

| # | 核心项 | 实现机制 | 本项目落点 |
| - | ------ | -------- | ---------- |
| L1 | **双层缓存鉴权** | DualCache: 内存→Redis→PG 逐级 miss 降级，密钥校验 0 DB 查询热路径 | auth.py 密钥校验加 Redis 前置层 |
| L2 | **成本计算器** | `completion_cost(tokens × price)` 结果塞进 `_hidden_params`，经响应头披露 | 虚拟密钥计费内核 |
| L3 | **异步记账管道** | spend 先入 Redis 队列，后台批量写 PG | 计费不阻塞推理主链路 |
| L4 | **ProviderConfig 转换层** | 每供应商一个 `transform_request/transform_response` 纯函数对 | 云适配器标准化改造 |

### 1.2 gateway (Portkey) —— 极简代理范式

源码实读（Hono 框架）：

- **122KB 体积 / <1ms 延迟**跑通 1600+ 模型路由——证明网关内核可以极轻
- Handler 完全对齐 OpenAI 全家族端点：chat/completions/embeddings/**images/speech/transcription/translation/realtime(WebSocket)/files/batches/finetune/messages**
- Redis 缓存后端可选挂载（`REDIS_CONNECTION_STRING` 检测式启用）
- **可借鉴**: ① `realtime` WebSocket handler 直接转发升级请求（本项目 websocket.py 可对齐）；② **条件中间件**（按 runtime 决定是否压缩）模式；③ 端点矩阵广度清单

### 1.3 one-api —— 渠道治理运营层

- **30+ 渠道协议适配**（含智谱/DeepSeek/Ollama/硅基流动等国内全量）
- 渠道级：多 Key 轮询 / 优先级 / 权重 / **失败自动禁用** / 一键测试验活
- 令牌级：额度 / 过期 / IP 白名单 / 模型限制 / 分组倍率
- **可借鉴**: 渠道"验活"管理动作（定时探活 + 手动测试按钮语义）——比本项目现有 `/health` 被动健康检查更主动

### 1.4 dify —— 应用平台层（远期参照）

- Workflow DAG 编排 / RAG Pipeline / Agent / 模型管理 / 可观测（Langfuse/Opik/Phoenix 集成）
- api/ 采用 **app_factory 模式 + uv 锁定 + import-linter 分层约束**（`.importlinter`）
- **可借鉴**: ① `importlinter` 分层防劣化（contracts: layers）——防止 utils 反向依赖 services；② E2E Playwright + seed fixtures 测试结构；③ Web 前端 `next/` 封装层（本项目未来前端可参照）

### 1.5 langgraph —— 有状态 Agent 运行时

- **Durable Execution**: 状态持久化 → 崩溃后从断点恢复；Human-in-the-loop 中断/恢复
- **可借鉴**: 本项目 `agents/yyc3_code_agent.py` 若走向生产 Agent，采用 checkpointer 状态快照模式；短期仅需吸收"状态外置到 PG"理念

### 1.6 ollama —— 本地推理锚点（主权基石）

- Go 单二进制 + llama.cpp/MLX 双后端；`cmd/launch/` 已内置 claude/codex/qwen 等 6 种 harness 集成
- **战略价值**: 本项目 DGX/Mac 推理池的**兜底层**——上游全断时 `ROUTER_ENABLED` 回退链最终落点是本地 Ollama，这就是"不受上游约束"的最后防线
- **可借鉴**: launch 子命令的组织方式（每集成一个文件，接口统一）

### 1.7 llama_index —— RAG 管道参照

- 重心已转 LlamaParse（agentic OCR/130+ 格式解析/ParseBench 基准）
- **可借鉴**: ① `llama-index-core` + integration 分包架构（核心与适配器分离——映射到本项目 core vs 云适配器）；② 文档解析基准测试意识（本项目 document_processor 可建 mini-ParseBench）

## 二、对比优势分析（本项目 vs 七项目）

| 维度 | 本项目 0379-World | 七项目最优 | 差距判定 |
| ---- | ---------------- | ---------- | -------- |
| 请求生命周期 | 中间件链+路由引擎 | litellm（异步记账/双层缓存） | 🟡 补 L1-L4 即平 |
| 端点广度 | chat/embeddings/rerank | Portkey（12+ 端点家族） | 🟡 按需补 images/asr |
| 渠道运营 | env 静态池+熔断 | one-api（多Key轮询/主动验活） | 🟡 补验活+多Key |
| 成本治理 | ❌ 无 | litellm（cost calculator+spend log） | 🔴 本次主攻 |
| 应用平台 | ❌ 无（API 层即终点） | dify（workflow/RAG 应用） | ⚪ 远期，暂不需要 |
| Agent 编排 | 单文件原型 | langgraph（durable/human-loop） | ⚪ 远期 |
| 本地推理主权 | Ollama 兜底已具备 | ollama 本身 | ✅ **领先** |
| 异构部署 | DGX/NAS/Mac 多端闭环 | 七项目均无此形态 | ✅ **领先** |
| 上游透明契约 | X-YYC3-Upstream 头 | 七项目均无等价物 | ✅ **领先** |
| RAG 管道 | pgvector 全链路 | llama_index（更全解析器） | 🟡 补解析格式 |

**结论**: 本项目定位（**自主可控的推理网关**）与七项目差异化清晰——不追平台大而全，
只补**成本治理 + 渠道运营 + 端点广度**三块，同时以"主权架构"为最高约束。

## 三、主权架构设计（不受上游约束的工程保证）

### 3.1 威胁模型与对策

| 上游风险 | 场景 | 对策（已有✅/规划🔧） |
| -------- | ---- | -------------------- |
| 涨价/停服 | 智谱/DeepSeek 政策变化 | ✅ 本地 DGX+vLLM 推理池；🔧 成本感知自动切换 |
| 限流/封禁 | API Key 被限 | ✅ 熔断+降级链；🔧 多 Key 轮询（学 one-api） |
| 协议变更 | OpenAI 格式漂移 | 🔧 L4 转换层标准化（学 litellm ProviderConfig）——**上游协议只污染单文件** |
| SDK 停维护 | 依赖库废弃 | ✅ 直接 httpx 裸调 OpenAI 兼容 REST，零 SDK 依赖（架构性正确） |
| 网络分区 | 公网中断 | ✅ fallback_url 双地址 + Ollama 本地兜底 |
| 数据出境合规 | 敏感数据 | 🔧 按模型标签路由：`sovereign_only` 模型白名单强制本地 |

### 3.2 数据平面完全自主清单

```yaml
推理主权:  DGX TP=2 (deepseek-v4-flash) + qwen3-embedding/reranker + Ollama 兜底  ✅
存储主权:  PostgreSQL 15 主从 (Patroni) + NAS 60TB 模型库                        ✅
缓存主权:  Redis 自建 (7/8)                                                     ✅
监控主权:  Prometheus+Grafana+Loki 自建                                          ✅
密钥主权:  env 静态 API Keys                                                    ✅ → 🔧 虚拟密钥(PG 自管)
协议主权:  OpenAI 兼容单格式进,转换层出                                          ✅ → 🔧 标准化 ProviderConfig
成本主权:  ❌ 无计量 → 🔧 本次补齐(L2 计价器),摆脱上游控制台看用量
应用主权:  API 层即终点(无需 dify 平台,本人即应用层)                              ✅ 按需
```

**判定**: 除成本计量外，数据平面已 100% 自主。补齐 L2 后达到完全主权。

## 四、技术核心项实施规划（P0→P2）

> 原则：**吸收范式、自研实现、零新增重量级依赖**（沿用 FastAPI+PG+Redis 栈）。

### P0-1 成本计量与虚拟密钥（学 litellm L1+L2+L3）｜3 个会话单元

```sql
-- 003_virtual_keys.sql (对齐本项目 schema 风格)
CREATE TABLE IF NOT EXISTS virtual_keys (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    key_hash VARCHAR(64) NOT NULL UNIQUE,        -- sha256, 明文只出现一次
    name VARCHAR(100) NOT NULL,
    owner VARCHAR(100) DEFAULT 'yanyu',
    model_whitelist TEXT[] DEFAULT '{}',          -- 空数组=不限
    monthly_budget_usd NUMERIC(10,4) DEFAULT 0,   -- 0=不限
    spent_usd NUMERIC(10,4) DEFAULT 0,
    rate_limit_tpm INT DEFAULT 0,                 -- 0=不限
    status VARCHAR(20) DEFAULT 'active',
    expires_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    metadata JSONB
);
CREATE TABLE IF NOT EXISTS spend_logs (
    id BIGSERIAL PRIMARY KEY,
    key_id UUID REFERENCES virtual_keys(id) ON DELETE SET NULL,
    model VARCHAR(100), upstream VARCHAR(100),   -- 记录 X-YYC3-Upstream 实际服务者
    prompt_tokens INT, completion_tokens INT,
    cost_usd NUMERIC(10,6), latency_ms INT,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_spend_logs_created_at ON spend_logs(created_at);
CREATE INDEX idx_spend_logs_key ON spend_logs(key_id, created_at);
```

实现要点：

1. **计价表** `model_prices`（JSON 配置即可）: input/output 每 1M token 单价；本地模型单价=0 但仍记 token（保用量可见性）
2. **记账管道**: 响应后 `BackgroundTasks` → Redis 队列 `LPUSH spend:queue` → 后台协程 `批量 BLPOP → PG 批量 INSERT`（学 L3，DB 写不进请求路径）
3. **响应头**: `X-YYC3-Cost-USDEST: 0.0021`（对齐现有 X-YYC3-Upstream 契约风格）
4. auth.py 校验链: 内存 dict → Redis → PG（学 L1 双层缓存）

### P0-2 上游池主动验活（学 one-api）｜1 个会话单元

- 复用 upstream_registry：新增 `async probe_all()`——按 `health_path` 并发 GET，连续 2 败标 `degraded`（不摘除，仅权重×0.5）
- 定时器: asyncio task 每 60s；管理端点 `POST /v1/admin/upstreams/probe`（auth 保护）
- Grafana 现有 dashboard 加"上游健康"面板（数据从 /metrics 出）

### P0-3 主权路由标签｜1 个会话单元

- Upstream dataclass 加字段 `sovereign: bool = False`（env 上游池 JSON 各项可选）
- 请求头 `X-YYC3-Sovereign: required` → 路由器硬过滤仅 sovereign 上游 → 无可用则 503（不降级到云）
- 用途: 敏感数据请求显式声明"只走本地"

### P1-1 多 Key 轮询（学 one-api）｜1 个会话单元

- `api_key_env: str` → `api_key_envs: List[str]`（向后兼容：单值仍接受）
- 轮换策略: 计数轮询 + 429 时跳到下一把（连续 3 把 429 → 触发现有熔断）

### P1-2 转换层标准化（学 litellm L4）｜2 个会话单元

```
services/providers/
  ├── base.py          # Protocol: transform_request(payload)->dict / transform_response(resp)->dict
  ├── zhipu.py         # 现 services/zhipu.py 改造
  ├── deepseek.py
  └── openai_compat.py # 覆盖 vLLM/NIM/Ollama-兼容
```

每个供应商协议变化只改单文件；新增供应商=新增一个文件+注册，路由器零改动。

### P1-3 端点广度补齐（学 Portkey 端点矩阵）｜按需

优先级: `/v1/audio/transcriptions`（ASR 上游已就绪，第四能力收口）> `/v1/images/generations`（Mac 数字人线第五能力）> realtime WS 转发对齐。

### P2（远期按需）

- importlinter 分层约束（学 dify，防架构劣化）
- 文档解析基准 mini-ParseBench（学 llama_index）
- Agent checkpointer 状态快照（学 langgraph，agent/yyc3_code_agent.py 生产化时）
