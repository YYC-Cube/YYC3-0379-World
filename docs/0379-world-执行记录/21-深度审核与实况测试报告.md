## 三、缺陷清单（按严重度排序）

### 🔴 P0-1：`canary_get()` Redis 直调无容错，Redis 故障 → 聊天主路径全量 500

- **位置**：`core/api/services/model_registry_svc.py:1240`
- **代码**：`data = _decode_hash(await redis_client.hgetall(_canary_key(alias)))` —— 裸调，无 try/except
- **调用链**：`POST /v1/chat/completions` → `chat.py:315 canary_route()` → `canary_get()` → Redis
- **证据**：本机 12 个集成用例失败堆栈全部终止于此帧；docstring 宣称「内存缓存 + 失败自动回退惰性判定」，但**失败回退分支并未实现**，注释与实现不符
- **生产影响**：Redis 宕机/网络分区瞬间，**所有聊天请求 500**（chat 是全平台核心入口）；且 Redis 客户端无连接超时上限配置（见 P1-2），单请求会被拖数秒至数十秒
- **修复**：`canary_get` 内对 `hgetall` 包 try/except，失败返回 None（语义=无灰度，直连 baseline），并记录 warning + 指标

### 🟠 P1-2：Redis 客户端零超时/零重试治理，故障时请求延迟劣化 10-30 秒

- **位置**：`core/api/cache.py:34-40`
- **代码**：`Redis(host=..., port=..., db=..., password=..., decode_responses=True)` —— 未设置 `socket_timeout` / `socket_connect_timeout` / `retry` / `health_check_interval`
- **证据**：集成测试实况——无 Redis 时单个 422/404 请求耗时 9-30s（test_video_tasks 4 用例耗时 226s）；冒烟冷启动首探针 39s
- **生产影响**：Redis 慢/不可达期间，每个走到 Redis 的调用点（限流、canary、TPM、记账、缓存）都叠加秒级惩罚；网关 P99 被拖垮
- **修复**：统一收口 Redis 客户端构造（connect_timeout≤2s、command_timeout≤3s、指数退避重试≤2 次、health_check_interval=30），并考虑给 canary/缓存读加进程内熔断（如 10s 半开探测）

### 🟠 P1-3：限流中间件故障降级后永不回切 Redis

- **位置**：`core/api/middleware/rate_limit.py:85-97`
- **代码**：`_redis_available` 一旦置 `False` 便永久短路（`if self._redis_available is False: return False`），**进程生命周期内不再探测恢复**；docstring 宣称「结果缓存 10 秒」与实现不符
- **生产影响**：Redis 瞬时抖动 → 限流永久退化为单实例内存模式，多副本网关限流失准且不自愈；docstring 误导后续维护者
- **修复**：改为「失败后置 False + 10s 时间戳，到期重探测」，恢复后自动切回 Redis 模式

### 🟠 P1-4：uvicorn `--workers 4` 下后台常驻任务每 worker 各起一份

- **位置**：`Dockerfile:87`（`--workers 4`）× `main.py` 4 个 startup 事件（probe 循环、vk 记账 ledger、registry merge consumer、heartbeat watch、Agent Worker lease、A2A 心跳）
- **生产影响**：4 worker = 4 份上游验活探针（探测流量 ×4）、4 份 A2A 心跳/租约竞争（30min lease 的互斥语义未被测试覆盖多实例场景）、4 份 merge consumer。BLPOP 消费虽不重复取数，但 PG 批量写与租约抢锁行为在 multi-worker 下未经证实
- **修复**：后台守护类任务单例化（独立 worker 进程/容器，或 `--workers 1` + 外部副本扩容 + leader 选举），或在文档中显式声明各循环的多实例安全性

### 🟡 P2-1：集成测试不密闭，强依赖 CI 的 Redis 主机名

- conftest 未注入 `REDIS_HOST`，依赖 docker-compose 服务名 `redis` 可解析；本机/外部贡献者无法跑通集成层，12 个用例必挂
- 且每个 Redis 触点的用例因连接重试多耗 30-60s，集成层全量 7-8 分钟（文档口径）主要耗在故障重试而非断言
- **修复**：引入 fakeredis（`pytest` 夹具替换 `app.cache.redis_client`），或 conftest 注入 `REDIS_HOST=127.0.0.1` + 快速失败短路

### 🟡 P2-2：测试覆盖率盲区集中在核心路由与文档处理

覆盖率 0% 的关键模块（快速层实测）：

| 模块 | 语句数 | 风险 |
|---|---|---|
| `services/model_router.py` | 197 | **EWMA 动态权重路由核心零覆盖**——README 头号卖点「智能调度」无直接测试 |
| `services/document_processor.py` | 101 | RAG 文档解析（PDF/DOCX）零覆盖 |
| `utils/crypto.py` | 45 | 加密工具零覆盖 |
| `api/orchestrator_entry.py` / `worker_entry.py` | 66 | 编排/worker 入口零覆盖 |

加上 `--cov-fail-under=0`，覆盖率无任何门禁约束。**修复**：为 model_router 的 EWMA 更新/选路/熔断恢复补纯单元测试（无需 Redis，纯内存状态机）；将 `--cov-fail-under` 先提到 45（当前 42），分阶段提升。

### 🟡 P2-3：文档口径与实测偏差

| 宣称 | 实测 |
|---|---|
| 快速层 ~0.3s | 19.78s |
| `canary_get`「失败自动回退惰性判定」 | 无失败回退实现 |
| 限流「Redis 检查结果缓存 10 秒」 | 永久闩锁，不回切 |
| 徽标「tests 400 passing」 | 本机全量 400 = 388 过 + 12 环境性失败 |

### 🟡 P2-4：其他观察项

1. **`/health` 未鉴权**（auth.py SKIP_AUTH_PATHS 含 `/health`）：对外暴露 CPU/内存/磁盘及 ollama/redis/pg 内部连通状态。作为 LB 探针合理，但经公网 Traefik 直达时属信息暴露面，建议边缘层限制来源网段或拆分 `/health`（内网明细）与 `/healthz`（公网存活）
2. **chat.py:334**：`canary_report_failure` 在 `except` 处理器内裸调用，Redis 故障时会二次抛异常掩盖原始错误路径——与 P0-1 同源，随 P0-1 一并加防护
3. **requirements.txt 全量宽松 pin（`>=`）**：与 CI 中 lint 工具显式 pin 的谨慎度不一致，存在依赖漂移风险；建议生产用 `requirements.lock`（仓库已有该文件，但 Dockerfile 用的是 requirements.txt）
4. **依赖 mypy/pyright**：mypy 仅 CI advisory 且不装于 dev requirements；pyrightconfig.json 存在但 pyright 不在任何门禁中——类型安全宣称与执行有落差

### 4.1 立即闭环（本周，P0/P1）

| # | 动作 | 验收标准 | 负责人建议 |

| 1 | `canary_get` 容错改造（P0-1） | Redis 宕机时 chat 请求仍 200 直连 baseline；新增「Redis 故障时 chat 可用」集成用例 | 网关 owner |

### 4.2 短期闭环（两周，P2）

1. **测试密闭化**：fakeredis 或 REDIS_HOST 注入，让集成层在本机/外部贡献者可跑；目标 `make test-integration` 在无 Docker 环境可运行
2. **覆盖率门禁**：`--cov-fail-under=45` 起步；优先补 `model_router.py`（EWMA 数学正确性、权重归一、熔断半开恢复）、`crypto.py`、`document_processor.py`
3. **文档校准**：修正 pytest.ini/README/Makefile 的耗时与行为宣称，注释与实现不一致处（canary_get、rate_limit）以代码为准回写
4. **依赖治理**：Dockerfile 生产层改 `requirements.lock` 安装；评估 requirements.txt 全量 pin

### 4.3 中期演进（1-2 月）

1. **故障演练制度化**：把「Redis 宕机 5 分钟」纳入发布前演练（现有 health-full.sh 17 项自检可扩展 chaos 项），验收：chat/embeddings/rerank 三能力降级有定义、告警有触发、恢复有回切
2. **Canary 闭环补全**：当前失败回退依赖 `canary_report_failure` + 惰性判定，建议补「自动回退后自动恢复探测」（weight 归零后定时小样本人工/自动提权策略），与现有 2min≥5 次回退形成完整闭环
3. **多实例一致性**：A2A 心跳租约、registry merge consumer 在 K8s/多副本下的 leader 选举或分片语义
4. **观测对齐**：为 P0-1 修复点新增 `yyc3_redis_degraded` 指标与告警（现有 backend_requests/TTFT/rollback 三件套之上），确保下次 Redis 故障时 5 分钟内可定位
5. **CI 矩阵**：补 Python 3.12 job（本机即 3.12.8，与 CI 3.11 存在版本差），避免「本机绿 CI 红/反之」的双轨漂移

### 4.4 长期演进方向

- **网关内核与业务面进程隔离**：路由/熔断/灰度（无状态）可多副本水平扩；记账/registry 守护（有状态）独立 Deployment，从根本上消除 P1-4 类问题
- **契约测试外扩**：当前 import-linter 已守内部分层，可对上游 OpenAI 兼容面引入 schema 契约测试（响应头 `X-YYC3-Upstream` 契约已有测试，扩至错误体结构）
- **质量度量看板**：把「本报告 12 项」转为可追踪 backlog，按月复盘关闭率，形成审计→修复→防回归的闭环
